# Load test — 200-user baseline (2026-08-10)

- **Commit:** `98a517b` (pre-v1.4.0)
- **Scenario:** 200 concurrent users · 30 challenges · 800 held-open WebSockets · ~9.5 min
- **Stack:** production `docker compose` (Caddy → single uvicorn worker → Postgres/Redis/MinIO), fresh DB
- **Backend limit:** 4 vCPU / 4 GB (a realistic mid-size event VPS)
- **Harness:** [`sim.py`](sim.py) · raw metrics: [`2026-08-10-baseline-result.json`](2026-08-10-baseline-result.json)

> **Resolved.** The v1.4.0 hardening (#174–#178 + #87 stage 1) has since been
> merged and re-tested — the collapse below is gone and goodput ~tripled. The
> verdict here describes the *pre-fix* baseline; see
> [Post-fix re-run](#post-fix-re-run--2026-08-10-c4bbc79) for the after.

## Verdict

**Holds at the door; buckles under sustained play — and it's concurrency-bound,
not CPU-bound.** The startup storm (200 logins + joins + 800 socket handshakes)
was a non-event. The failure is the sustained refetch storm every solve
triggers, colliding with a 15-connection database pool, compounded by
request-blocking fan-out (one announcement to all participants took **24
seconds**). Throughout the collapse the backend used under half its CPU budget,
so adding cores would not help. This is architectural and fixable without
abandoning the single-process design (ADR-0005).

## Bottlenecks found (→ v1.4.0 work)

Ordered by impact. Each links the tracking issue; every claim is grounded in
code (`file:line` in the issue).

1. **Activity-room refetch storm × tiny DB pool** — [#175](https://github.com/tbcsec/Flagpost/issues/175) + [#174](https://github.com/tbcsec/Flagpost/issues/174).
   One solve pings all clients; each refetches `["challenges"]`; hundreds of GETs
   queue behind 15 connections. *This is the first cliff.*
2. **Foreground fan-out blocks the event loop** — [#176](https://github.com/tbcsec/Flagpost/issues/176).
   Announcement/scoreboard broadcasts are awaited inside the mutation (the 24 s
   announcement). Move them to the existing background lane (ADR-0012).
3. **Sequential broadcast, no per-send timeout** — [#177](https://github.com/tbcsec/Flagpost/issues/177).
   One slow socket stalls the whole room (the 5.1 s stall).
4. **Unthrottled WS handshake + snapshot-per-join** — [#178](https://github.com/tbcsec/Flagpost/issues/178).
   A reconnect herd recomputes a scoreboard per socket.
5. **Scoreboard recompute + full-board egress** — [#87](https://github.com/tbcsec/Flagpost/issues/87).
   Real, but *not* the first cliff — reframed after this test (its original
   "fine to ~1,000 concurrent" premise was wrong; it showed seams at 200).

## The one chart that explains it

The DB pool rides its 15-connection cap in every burst while CPU sits well under
half its budget — the signature of a concurrency bottleneck, not a compute one.
(Raw series in the JSON; `pg_conns` vs `cpu` samples.)

```
DB pool util   ▁▁▂█▁▁█▁▂██▂▁  ~100% of cap, repeatedly
Backend CPU    ▂▁▂▄▁▂▄▁▂▄▂▁▁  ~10–42% of a 4-core budget
               └────────── steady play ──────────┘
```

## Caveats

- Absolute p95/p99 latencies are inflated by client-side queueing once the
  harness's own pool saturated — treat them as "congestion collapse," not exact
  SLAs. The server-side signals (pool pinned at 15, 24 s announce, idle CPU) are
  ground truth and independent of that.
- 200 real browsers open ~6 connections/origin each — *more* concurrency than
  the harness generated, so real load would be at least this bad.
- Single host, loopback, one IP, isolated Postgres — see [`README.md`](README.md)
  § "Honest limits".

## Post-fix re-run — 2026-08-10 (`c4bbc79`)

Same harness, same scenario, fresh stack carrying all six fixes (#174–#178 +
#87 stage 1). The catastrophic, request-blocking failures are **gone**, and the
system no longer collapses at 200 — it sustains **~3× the goodput** at
dramatically better median/p95, then degrades gracefully at a much higher load.

| Metric | Baseline (`98a517b`) | Post-fix (`c4bbc79`) | Change |
|---|--:|--:|--:|
| **Announcement POST** (all 200) | 24,423 ms | **29 ms** | **832× faster** |
| Submit p50 | 25 ms | 19 ms | 1.3× |
| Submit p95 | 39,590 ms | 11,644 ms | **3.4× faster** |
| Refetch p50 | 3,875 ms | 1,794 ms | 2.2× faster |
| Refetch p95 | 198,939 ms | 109,168 ms | 1.8× faster |
| Login p95 | 327 ms | 284 ms | 1.2× |
| Slow-client solve delivery | ~5.1 s (head-of-line) | off the submit path | eliminated |
| **Solves completed** (goodput) | 274 | **800** | **2.9×** |
| Submissions completed | 1,149 | 3,626 | 3.2× |
| DB pool peak | **15 / 15 (pinned)** | 41 / 40 | ceiling raised 2.6× |
| Backend CPU peak | 167 % / 400 % | 124 % / 400 % | still not CPU-bound |

### What the fixes demonstrably did

- **#176 (background fan-out)** turned the 24.4 s announcement into **29 ms** — the single clearest win.
- **#174 (pool)** removed the hard 15-connection ceiling; under the heavier post-fix load the pool now works up to its new 40-cap instead of pinning at 15.
- **#177 (parallel broadcast)** + **#176** took the scoreboard fan-out off the submit path — the ~5.1 s slow-client head-of-line stall no longer touches a submit.
- **#174 + #175 (coalesce + jitter)** roughly **halved** refetch latency and let the system clear **~3× more work** in the same wall-clock.

### Honest reading of the remaining tail

Submit p99 (119 s) and refetch p95 (109 s) are still high — but this is a
**closed-loop** test: because responses are now fast, each simulated client
loops and issues its next request instead of blocking, so the post-fix run
offers **~3× more load** than the baseline could. The tail is the harness
driving the *now-healthy* system to a new saturation point where (a) the raised
40-connection pool becomes the next ceiling (it reaches 41), and (b) the
harness's own 400-connection pool re-saturates and inflates the absolute
numbers — the same caveat that applied to the baseline. It is **not** the same
load 2× faster; it is a system that no longer falls over at 200 and now has
headroom to a materially higher throughput.

> Note: the tool's printed footer still labels the pool cap "5 + 10 = 15" — a
> stale string baked into `sim.py`'s reporter; the live cap this run was 40
> (`db_pool_size` 20 + `db_max_overflow` 20), confirmed by the observed peak of 41.

### Next ceiling

At ~3× throughput the finite DB pool + the inherent per-solve refetch volume are
what bend next. Closing that is **#87 stage 2** (delta / top-N broadcasts to cut
per-solve egress) and further pool tuning — both post-v1.4.0 unless a real event
shows egress is the binding constraint. The v1.4.0 goal — *don't collapse at a
200-person event* — is met.
